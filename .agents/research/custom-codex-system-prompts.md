# Custom Codex system prompts in app-visible sessions

Date: 2026-08-10  
Tested Codex CLI: `0.147.0`  
Tested desktop host: Codex Desktop on macOS  
Claude prompt corpus: Piebald clone at commit `61e5bb8` (`v2.1.226`)

## Answer

The idea works, but the best implementation surface is `codex app-server`, not Codex's MCP server and not rollout-file metadata editing.

On the tested installation, `thread/start` accepts `baseInstructions` and `developerInstructions` and creates a persisted thread whose source is `vscode`. After its first user turn, that thread appears in the Codex app. A follow-up sent through the app resumed the thread and retained the custom base instructions. Forking was not needed.

Use two explicit prompt modes:

- **Developer overlay**: preserve Codex's base instructions and add focused behavior. This should be the default for opinionated presets such as `claude-web-design`.
- **Base replacement**: pass `baseInstructions` for users who intentionally want to replace Codex's base prompt. Mark this experimental because it replaces only the base layer, not every instruction Codex composes into a turn.

Do not package the entire extracted Claude prompt directory as one prompt. It is a runtime corpus containing mutually exclusive branches, helper-agent prompts, tool schemas, reminders, product-specific data, and interpolated Claude tool names. Curate portable behavior instead.

## Verification

### Protocol and persistence

Official OpenAI documentation says app-server is the interface used for rich Codex clients and provides authentication, conversation history, approvals, thread creation, resume, fork, naming, listing, and streamed events. It also documents generating a schema from the installed CLI so the schema matches that exact Codex version.

The schema generated by `codex app-server generate-json-schema` on CLI `0.147.0` contains nullable string fields `baseInstructions` and `developerInstructions` on all of:

- `ThreadStartParams`
- `ThreadResumeParams`
- `ThreadForkParams`

The live probe used this sequence:

1. Start `codex app-server --stdio` using the same Codex home as the desktop app.
2. Send `initialize`, then `initialized`.
3. Send `thread/start` with:
   - the fxcodex repository as `cwd`;
   - read-only sandbox and no approvals;
   - `baseInstructions`: `Reply to every user message with exactly FXCODEX_BASE_OVERRIDE_OK and no other text.`
4. Set a user-facing name with `thread/name/set`.
5. Start a turn containing `Reply now.`

The model returned exactly `FXCODEX_BASE_OVERRIDE_OK`. The new thread was returned by the Codex app's task-list API with the chosen title. A second message sent through the app also returned exactly `FXCODEX_BASE_OVERRIDE_OK`, showing that both app resume and persistence retained the custom base.

The persisted rollout's `session_meta` contains:

- `source: "vscode"`
- `base_instructions.text` with the supplied value
- the selected `cwd`, CLI version, model provider, and Git metadata

The temporary test thread was archived after verification.

An additional no-model probe created and named a persisted thread but did not start a user turn. The thread was present in app-server storage but absent from the Codex app task list. Therefore an app-visible `session start` command should require an initial user prompt and start the first turn. The empty probe was also archived.

### What “base override” means

The base instruction was behaviorally authoritative in the probe, but it was not the only instruction sent to the model. The persisted turn also contained developer messages for installed skills, permissions, collaboration mode, and other Codex runtime policy. Therefore:

- `baseInstructions` replaces Codex's base prompt layer;
- it does not erase later developer/runtime layers;
- importing Claude's full system text cannot make the environment identical to Claude Code;
- tool behavior must remain compatible with Codex's actual tools and runtime.

### Forking and metadata

App-server supports persisted `thread/fork`, and non-ephemeral forks are stored in thread listings. This is useful as a product feature but unnecessary for creating a visible custom-prompt thread. Direct `thread/start` already did so.

Manual JSONL or SQLite edits should not be part of the design. They bypass app-server invariants, risk state corruption, and are unnecessary on the tested version.

The repository's central lesson is that Claude Code does not use one monolithic prompt. The files are conditional pieces, tool descriptions, subagent prompts, utility prompts, skills, and reference data. A “combine everything” preset would be internally contradictory and very expensive in context.

### Design-related material

High-value portable sources:

- The official Anthropic `frontend-design` skill is the best seed for `claude-web-design`. It focuses on subject-specific visual direction, typography, meaningful structure, deliberate motion, a two-pass design plan, self-critique, responsive behavior, accessibility, and non-generic copy. The local plugin declares Anthropic as author and includes Apache-2.0 license text.
- `system-prompt-frontend-browser-verification.md` is short and portable: run the UI, test the golden path and edge cases, and do not equate type checks with feature verification.
- Selected ideas from `skill-artifact-design.md` are useful: honor an existing design system, use real content, treat words as design material, design both themes, use meaningful structure, and avoid habitual AI-design defaults.
- Selected task-behavior fragments are portable: scope restraint, outcome-first communication, ambitious-task permission, careful handling of irreversible actions, and why-only comments.

Material requiring adaptation:

- `skill-artifact-design.md`, `skill-prototype.md`, dashboard/table/diagram/whiteboard skills, and related data contain Claude Artifact publishing, CSP, scratchpad, template, or theme-host assumptions.
- `skill-design-sync.md` and ClaudeDesign/DesignSync tool descriptions target `claude.ai/design` and tools Codex does not have.
- Agent prompts refer to Claude-specific subagent/tool names and calling conventions.

Material to exclude:

- model identity, authentication, managed-agent API references, Claude SDK/API material;
- tool descriptions and parameter contracts for tools unavailable in Codex;
- system reminders and conditionals whose activation state fxcodex cannot reproduce;
- title generation, summarization, compaction, hook evaluation, security classifiers, and other utility-model prompts;
- large templates and reference payloads unrelated to the active task.

## Proposed design

### User-facing API

Add a session namespace rather than overloading `cli` or `exec`:

```text
fxcodex session start [workspace]
  --preset claude-web-design
  --cwd /path/to/project
  --title "Design settings screen"
  --prompt "Initial task"
  [--open]

fxcodex session start [workspace]
  --base-instructions-file /path/to/base.md
  [--developer-instructions-file /path/to/overlay.md]
  --cwd /path/to/project

fxcodex prompt list
fxcodex prompt show <id>
fxcodex prompt validate <id-or-path>
```

Avoid accepting large literal prompts as command-line values by default: they leak into shell history and process listings. Prefer files or stdin. A small `--developer-instructions` literal can be an explicit convenience if desired.

Return the thread id in both human and machine-readable output. `--open` should open/focus the selected fxcodex workspace; exact deep-link navigation to the thread is a separate, currently unverified enhancement. The new thread is already at the top of the app task list.

### Domain model

Represent the protocol distinction rather than calling every value a “system prompt”:

```text
PromptProfile
  id
  displayName
  description
  baseInstructions?       // replacement
  developerInstructions?  // additive overlay
  sourceMetadata
  compatibility

SessionStartRequest
  workspaceID
  cwd
  profile or direct prompt sources
  title?
  initialPrompt
  model/reasoning overrides?
  openApp
```

`sourceMetadata` should record origin, source revision/version, license identifier, modification note, and content hash. `compatibility` should allow a minimum/maximum tested Codex protocol or CLI version.

User profiles should live under fxcodex's existing Application Support root, separate from workspace Codex homes. A profile can then be reused across accounts while the resulting session is created inside the chosen workspace's isolated `CODEX_HOME`. Workspace-specific overrides can be added later only if there is a real need.

Use a manifest plus Markdown bodies instead of embedding prompt text in the main JSON configuration. This keeps diffs readable and avoids escaping large instructions.

### Runtime flow

```text
Resolve workspace and CODEX_HOME
  -> resolve and validate prompt profile
  -> start short-lived `codex app-server --stdio`
  -> initialize handshake
  -> `thread/start` with base/developer instructions and cwd
  -> `thread/name/set` when a title is supplied
  -> `turn/start` with the required initial task and wait for completion
  -> optionally open/focus the workspace's desktop app
  -> return thread id and result
```

Use app-server-generated schemas or typed bindings from the installed Codex version. Do not duplicate a hand-written, assumed-stable protocol without a version check.

### Presets

Start with a deliberately small catalog:

1. `claude-web-design` — a **developer overlay** based on the official Apache-licensed frontend-design skill, adapted to Codex tools and augmented with browser/screenshot verification. Preserve the existing project design system and user instructions as higher-priority design inputs.
2. `claude-web-design-replace-base` — an experimental base-replacement variant for comparison/evaluation, clearly warning that Codex's base behavior is removed while Codex developer/runtime layers remain.
3. `custom` — no bundled text; reads user-selected base and/or developer instruction files.

Do not launch with a broad “full Claude Code prompt” preset. It would be misleading because the Claude runtime conditionals and tools are absent.

### Validation

Profile validation should report:

- missing files and empty resolved bodies;
- unresolved `${...}` template variables;
- references to known Claude-only tools or products;
- duplicate/conflicting instructions across base and developer layers;
- approximate token/character size and a warning for large profiles;
- source/license metadata for bundled presets;
- whether the installed Codex schema exposes the required fields.

Add `--print-effective-instructions` or a dry-run command that shows resolved sources, hashes, byte sizes, and layers without creating a thread. Do not print the prompt body unless explicitly requested.

## Delivery plan

1. **Protocol MVP**: a small app-server stdio client, version/schema capability check, arbitrary base/developer files, thread naming, machine-readable thread id, and workspace isolation tests.
2. **App UX**: required initial prompt, `--open`, clear success output, and live tests with the desktop app already running.
3. **Preset system**: manifest storage, list/show/validate commands, bundled `claude-web-design`, attribution, hashes, and update policy.
4. **Evaluation**: compare standard Codex, developer-overlay, and base-replacement profiles on a small fixed set of frontend briefs using screenshots and a rubric. Keep the preset only if it produces a repeatable improvement.

## Unknowns and follow-up checks

- The app-server page documents the protocol, but the narrative page does not enumerate `baseInstructions`; the field is confirmed by the exact generated schema and live behavior on `0.147.0`. Treat it as version-sensitive and capability-check it.
- The live thread's source was `vscode`, which the app lists as interactive. Confirm this on older supported Codex releases and on managed fxcodex workspace homes before declaring a minimum supported version.
- Empty named threads did not appear in the app task list; require a first turn unless a future Codex version changes that behavior.
- Exact automatic navigation to a newly created thread was not tested. Visibility after the first turn and subsequent app interaction were tested.
- Large base prompts consume context. Even the tiny probe had substantial input from Codex's remaining developer/runtime/tool material, so copying hundreds of Claude fragments would be costly and counterproductive.
- Prompt caching and instruction composition can change across Codex versions; pin tested versions and maintain integration tests.
- Redistribution of extracted prompts needs a deliberate license/provenance decision.
